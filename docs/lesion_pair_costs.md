# Generate lesion pair costs



> The baseline (BL) and follow-up (FU) lesions have been aligned, and now we need to calculate a cost for each possible combination of "BL lesion - FU lesion" to facilitate the later matcher in determining which lesions are more likely to be the same lesion.

The lower the cost calculated here, the more similar and likely the two lesions are to correspond under the current rules.

But special attention:

This stage will not determine the final lesion correspondence. 

That is to say, here we are only "generating candidate edges+calculating costs for candidate edges", rather than directly saying:

```text
BL1 must correspond to FU2
```

Separating 'cost calculation' and 'final allocation' is to enable the subsequent matcher to handle:
- Ordinary one-on-one matching;
- BL lesions disappeared in FU;
- New lesions appear in FU;
- Multiple BL lesions merge into one FU lesion (many to one/MERGING).


At this stage, it is necessary to read the CSV generated by the following python program:

```text
tools/extract_aligned_lesion_features.py
```

This extractor will record the centroids of both BL and FU lesions in a unified format:
```text
FU_RAS_mm
```

coordinate space.

This is very important: We cannot directly calculate the distance between the original BL coordinates and the original FU coordinates. Because BL and FU may not have been in the same space originally. Only after registration, can they be unified to 'FU_SAS_mm' for spatial distance to be meaningful.


```text
src/lesion_pair_costs.py
    Pair-cost calculation, validation, candidate generation and matrix export.

tools/generate_lesion_pair_costs.py
    Command-line interface for one or more aligned lesion-feature CSV files.

tests/test_lesion_pair_costs.py
    Acceptance-oriented automated tests.

tests/demo_lesion_pair_costs.py
    Small two-patient demonstration that requires no imaging files.
```


## Candidate generation

The candidate lesion combination is generated separately within each patient

Assuming a patient has:

```text
N baseline lesions
M follow-up lesions
```

So by default, it will generate:

```text
N × M BL-to-FU edges
```

That is, the Cartesian product of BL and FU.

For example:

```text
BL1 ──► FU1
BL1 ──► FU2
BL2 ──► FU1
BL2 ──► FU2
```

If BL has 2 lesions and FU has 2 lesions, there will be 4 possible combinations.

For now, we cannot determine who and who are the true corresponding lesions.

### not generate candidates across patients

For example:

```text
patient_A's BL1
```

Absolutely not with:

```text
patient_B's FU2
```
Generate a candidate edge.

All candidate edges must belong to the same patiend_id.

---

### Optional distance filtering: `--max-distance-mm`

Can be used:

```text
--max-distance-mm
```

Set a maximum spatial distance.

For example:

```text
--max-distance-mm 100
```

If the distance between a BL lesion and a FU lesion exceeds 100 mm, then this combination will not be considered as a candidate pairing directly.

Pair deleted from the distance gate:

- Will not appear in the long form candidate table;
- In the cost matrix, it will be written as:

```text
inf
```

which is infinity.


Candidate generation does not specify:

```text
One FU lesion can only correspond to one BL lesion
```

So it is entirely possible to keep this candidate:

```text
BL1 ──► FU4
BL2 ──► FU4
BL3 ──► FU4
```

Which is

```text
Multiple BLs → Same FU
```

It can still exist. This design is intentional.

Because during the previous inspection of Cohort A's expert correspondence, it was discovered that:

```text
MERGING
```
situation like this.

That is to say, in real data, there may indeed be: Multiple BL lesions merge into one lesion during FU.

If this stage forces one to one in advance, then before entering the real matchmaker, 'MERGING' has already been artificially excluded.

So the possibility of many to one must be preserved here.


# Cost components

Each candidate edge will not only output a final total cost.

The program will also save each part that makes up this cost separately.


The advantage of doing this is that in the future, if the cost of a certain pair is very high or low, we can directly check whether it is "too far away", "too much difference in size", or "too big difference in PET" instead of getting a completely incomprehensible black box score.

At present, cost mainly consists of three parts:

1. Spatial distance;
2. Differences in lesion size;
3. Optional PET differences.


## 1. Spatial distance

Firstly, calculate the Euclidean distance based on the aligned centroid of the lesion:

```text
distance_mm = sqrt(
    (BL_x - FU_x)^2 +
    (BL_y - FU_y)^2 +
    (BL_z - FU_z)^2
)
```

That is, the distance between straight lines in ordinary three-dimensional space.

The coordinates must come from:

```text
FU_RAS_mm
```

### distance_cost

A simple 'distance_mm' may be relatively large, for example:

```text
10 mm
30 mm
80 mm
```

To make it easier to mix with other cost components, the distance will be divided by a scale:
```text
distance_cost = distance_mm / distance_scale_mm
```

Default:

```text
distance_scale_mm = 50 mm
```

For example:

```text
distance_mm = 25 mm
distance_scale_mm = 50 mm
```

So:

```text
distance_cost = 25 / 50 = 0.5
```


50 mm is not a hard threshold, which can be easily misunderstood here.

```text
distance_scale_mm = 50
```

It does not mean that it cannot be matched if it exceeds 50 mm.

It just:

```text
normalisation / scale factor
```

That is, it is used to scale the distance cost.

The parameter that is truly responsible for "deleting the candidate directly if it exceeds a certain mm" is:

```text
max_distance_mm
```

So:

```text
distance_scale_mm
```

And

```text
max_distance_mm
```

They are two different things.

---

## 2. Lesion size difference

If size weighting is enabled, the following will be used:

```text
volume_ml
```

participate in cost calculation.

we are currently using symmetric fractional difference:

```text
size_difference = |V_BL - V_FU| / max(V_BL, V_FU)
```

It can be simply understood as looking at the difference in volume between two lesions and dividing it by the larger of the two volumes.

For normal positive volume:

```text
0.0=Two lesions with identical volumes
The closer it is to 1.0, the greater the difference in volume between the two lesions
```

For example:

```text
BL = 10 ml
FU = 10 ml
```

So:

```text
size_difference = 0
```

if:

```text
BL = 10 ml
FU = 5 ml
```

So:

```text
size_difference
= |10 - 5| / max(10, 5)
= 5 / 10
= 0.5
```

This value will also be stored in:

```text
size_cost
```


### Why is it said to be symmetrical?
Because:

```text
BL = 10, FU = 5
```

and：

```text
BL = 5, FU = 10
```

the result obtained is the same.

Which is ：

```text
cost(BL, FU) = cost(FU, BL)
```

At least the size part is symmetrical.



## 3. Optional PET difference

ET is optional.

The reason is that currently, not every patient in Cohort A's development data may have PET data that can be safely used.

supported PET feature：

```text
none
suvmean
suvmax
pet_mean
pet_max
```

by default：

```text
suvmax
```

### `suvmean` / `suvmax`

Only when SUV data really exists in CSV will it be used.

The current aligned length feature extractor is only available in:

The input PET is clearly declared as having undergone SUV calibration

Only in this case will the SUV field be filled in.

Therefore, the program will not treat any PET intensity as an SUV.


### `pet_mean` / `pet_max`

If using the original:

```text
pet_mean
pet_max
```

BL and FU must have:

```text
Same and non empty pet_units
```

Otherwise, they wouldn't be compared.

This is to avoid such errors:

```text
The PET intensity unit of BL is A
The PET intensity unit of FU is B
```

But the program directly calculates the difference.

If the units are not consistent, this difference is actually meaningless.


### PET difference formula

Only when PET data exists and can be reasonably compared, calculate:

```text
pet_difference = |PET_BL - PET_FU| / max(|PET_BL|, |PET_FU|)
```

For example:

```text
PET_BL = 8
PET_FU = 6
```

So：

```text
pet_difference
= |8 - 6| / max(8, 6)
= 2 / 8
= 0.25
```

# Combined cost

Default weight:

```text
distance_weight = 1.00
size_weight     = 0.50
pet_weight      = 0.25
```
But it's not just about forcibly adding all terms here.

For each candidate, only the truly available components participate in the calculation.

Formula：

```text
total_cost =
    sum(weight_i × component_cost_i)
    ------------------------------------
          sum(active weights)
```

First, multiply each effective cost by its corresponding weight, then add them up, and finally divide by the total number of weights that actually participate in the calculation.


## total_cost

The lower the total cost, the more similar the two lesions are in the current cost model.

But：

```text
total_cost
```

Is Not probability.

So we cannot say that：

```text
cost = 0.2
```

Is represents:

```text
80% chance it is the same lesion
```

It is just a candidate edge score for subsequent matchers to use.

## Long-form output

`lesion_pair_costs.csv` contains:

| Column | Meaning |
|---|---|
| `patient_id` | Patient owning both lesions. |
| `bl_lesion_id` | Temporary/aligned BL lesion ID. |
| `fu_lesion_id` | Temporary/aligned FU lesion ID. |
| `distance_mm` | Euclidean aligned centroid distance. |
| `distance_cost` | Distance divided by `distance_scale_mm`. |
| `bl_volume_ml` / `fu_volume_ml` | Lesion volumes used by the size term. |
| `size_difference_fraction` | Symmetric fractional volume difference. |
| `size_cost` | Size contribution before weighting. |
| `pet_feature` | Requested PET feature. |
| `bl_pet_value` / `fu_pet_value` | PET values when present. |
| `pet_difference_fraction` | Symmetric PET difference when comparable. |
| `pet_cost` | PET contribution before weighting. |
| `pet_used` | Whether PET genuinely contributed to this pair. |
| `active_weight_sum` | Sum of weights actually active for this candidate. |
| `total_cost` | Combined weighted candidate cost. |
| `candidate_rank_for_bl` | Cost rank among candidates for the same BL lesion. |

`candidate_rank_for_bl` is provided only for inspection. Rank 1 does not mean
that the lesion has already been matched. The later global matcher may make a
different decision once unmatched penalties, merge topology, and other graph
constraints are considered.

## Cost matrix output

The tool writes one CSV matrix per patient:

```text
outputs/lesion_pair_cost_matrices/
├── patient_01_cost_matrix.csv
├── patient_02_cost_matrix.csv
└── ...
```

Rows are BL lesion IDs and columns are FU lesion IDs:

```csv
bl_lesion_id,FU_L001,FU_L002,FU_L003
BL_L001,0.12,0.83,1.21
BL_L002,0.74,0.09,0.95
```

When a spatial gate removes a candidate, the matrix cell is `inf`.

The matrix can therefore be consumed directly by a future matcher, while the
long-form CSV remains useful for debugging and explaining why a particular edge
has a low or high cost.

## Input validation

The implementation intentionally raises clear errors when:

- required patient/timepoint/lesion ID fields are missing;
- aligned centroid coordinates are missing or non-finite;
- `coordinate_space` is present but is not `FU_RAS_mm`;
- duplicate lesion IDs occur within one patient/timepoint;
- size weighting is requested but `volume_ml` is missing, non-finite, or <= 0;
- cost weights/scales are invalid.

Optional PET does not make the whole cost-generation step fail merely because a
patient lacks PET.

3. aligned Euclidean distance is calculated correctly;

## Acceptance-criteria mapping

### Candidate lesion pairs are generated within each patient

Implemented by `generate_lesion_pair_costs()` using a separate BL × FU Cartesian
product for every `patient_id`. No cross-patient candidate edges are created.

### Spatial distance is calculated using aligned lesion coordinates

Implemented using Euclidean distance over `centroid_x_mm`, `centroid_y_mm`, and
`centroid_z_mm`. When `coordinate_space` metadata is supplied, the implementation
requires `FU_RAS_mm`.

### Lesion size differences can contribute to the cost

Implemented using the symmetric fractional difference of `volume_ml`, controlled
by `size_weight`.

### PET feature differences can be incorporated where appropriate

Implemented as an optional feature term. SUVmean/SUVmax can be used when
available; raw PET mean/max requires matching units. Missing PET does not cause a
false zero-difference assumption.

### A cost matrix can be produced for the matcher

Implemented by `PatientCostMatrix` and `export_cost_matrices()`. One labelled
BL × FU CSV matrix is written for every patient.

## Deliberately out of this stage's scope

This iteration does not:

- select the final lesion correspondence;
- add unmatched/disappearing/new-lesion graph edges;
- infer `MERGING` or other topology classes;
- use the expert correspondence CSV as an input feature;
- optimise the weights from expert labels;
- run NetworkX min-cost-flow.

Those belong to the downstream matcher/evaluation stages. Keeping them separate
prevents evaluation ground truth from leaking into candidate feature generation.
